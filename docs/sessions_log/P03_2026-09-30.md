# P03 — Performance step 2: compiled training at fixed shapes + pure-fp16 inference (2026-09-30, Mac, CPU only)

## Why
Dom asked whether the model could be pushed further toward being compute-bound. After the T4 profile (P02), matmuls,
convs and attention were only 29–56% of GPU kernel time; the rest was bandwidth-bound LayerNorm, casts and elementwise
ops. The two biggest levers that don't change the architecture: torch.compile in *training* (it was only measured in
inference: −37 to −48%), and running inference in pure fp16 instead of autocast (casts + fp32 LayerNorm were 58% of
Track B inference).

## What was built
- `src/knee/model/compiled.py`: `plan_chunks` / `encode_chunks` split a bag into bucket chunk sizes so the compiled
  encoder only sees a few shapes; `compile_module` (in-place `nn.Module.compile`, `dynamic=False`, recompile limit
  raised); `to_half` / `is_half`.
- `KneeViT.compile_encoder`, `TrackAModel.compile_encoder` + `use_channels_last`; both `encode_windows` now go through
  `encode_chunks` and feed the encoder in its own dtype.
- `SlicePosEmbed` builds its frequencies in fp32 per call (as a buffer, `model.half()` would round 2π·2⁷ to a 0.5 step)
  and casts its features to the projection's dtype.
- `train_sup` `perf` block (`compile`, `compile_mode`, `buckets`, `min_bucket`, `channels_last`; turns on
  `cudnn.benchmark` when compiling); `pretrain_mae` `perf.compile`.
- `predict.load_arm(ckpt, device, perf)` + `run_arm` (no autocast for a half model; fp32 retry flips the model to
  fp32 and back, which is lossless); `notebooks/infer.py` reads `perf` from `arms.json` (per-arm override allowed).
- `notebooks/kaggle_profile/gpu_profile.py`: `PROFILE_SET=step2` (default) measures eager vs compiled for every
  workload while cycling 3 realistic bag sizes, plus pure-half inference, the compute share, graph counts and fp16
  feature error. CPU smoke run passes; **not pushed to Kaggle** (Dom: wait).
- `tests/test_compiled.py` (14 tests). Full suite: 131 passed, 2 skipped.

## Results
None on a GPU yet. CPU: bucketed SliceViT equals the plain split (values and gradients, train and eval); Track A
bucketed equals plain in eval; fp16 window features within 0.04% (Track B) / 0.15% (Track A) of fp32 with random

### Learning notes
1. **Why compile needs fixed shapes.** Inductor generates kernels specialized to tensor sizes. A new size means a new
   compile (tens of seconds), or a dynamic-shape graph that's slower. Splitting 44 windows as 32 + 8 + 4 means any bag
   size reuses the same few compiled graphs.
2. **Why padding with copies, not zeros.** For a ViT it doesn't matter (each window is independent). For a CNN with
   BatchNorm in training, zeros would drag the batch mean/variance toward 0 and change every real window's output;
   copies keep the statistics close.
3. **Autocast vs pure half.** Autocast keeps fp32 master weights and decides per op; for LayerNorm and softmax it
   picks fp32, so every LayerNorm costs a cast in, fp32 traffic, a cast out. Pure half drops all that. LayerNorm's
   kernel still accumulates its mean/variance in fp32 internally, which is why it stays accurate.

## Addendum: item 3, bigger matmuls (Dom asked, same session)
- `train_sup`: `optim.effective_batch` (accum derived; must divide), `data.eval_batch_size` for the per-epoch eval.
  Configs set `effective_batch` to the old accum (no change) and `eval_batch_size: 4`.
- `predict`: `arm_sample` / `collate_arm` split out of `arm_input`; `predict_dirs(..., studies_per_forward)` groups
  preprocessed studies per forward and retries a failed group one study at a time; `load_arm` `perf.window_chunk`.
  `notebooks/infer.py` reads `perf.studies_per_forward`.
- Profile: `+bs2/+bs4` Track B training, `+4studies+chunk128` (B) and `+4studies+chunk32` (A) inference; ms per study.
- Tests: grouped = single predictions (and the one-by-one retry), `effective_batch` → accum. 133 passed, 2 skipped.
- Honest expectation: modest (UNVERIFIED 5–15%). GEMMs are already ~16k rows; ViT-S's 384 width is the real limit.
  Track A training at batch 2 likely won't fit the T4 without checkpointing (11.3 GB at batch 1), so it isn't profiled.

**Learning note: what "bigger matmuls" can and can't fix.** A GEMM's efficiency depends on all three sizes
(M rows × K inner × N out). Batching more studies only grows M. Once M is in the thousands, the tensor cores are
already busy, and what's left is K and N (the model width), which only a wider model changes.
