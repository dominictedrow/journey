# P04 — Both Kaggle T4s: sharded inference + two folds at once (2026-09-30, Mac, CPU only)

## Why
Kaggle GPU sessions have two T4s and everything so far used only GPU 0 (P02 profile). Dom: "implement both T4s".
Two places benefit: the inference notebook (the efficiency score is linear in runtime) and Track A training
(~14 T4-h per fold, 5 folds ≈ 70 h of the ~90 h quota left).

## What was built
- **Inference** (`src/knee/infer/predict.py`): `predict_dirs_multi` runs one spawned process per GPU. Each process
  loads every arm itself (a compiled model can't cross processes), runs its own DataLoader workers, and predicts a
  cost-balanced share of the studies (`shard_studies`: greedy by series count from `test_series.csv`). Children
  return raw per-arm probabilities and the parent blends once over all studies (`combine_raw`), so a **rank blend
  stays correct** and the submission is identical to the one-GPU path. A dead child (CUDA error, host OOM) is re-run
  once in the parent on its device; if that also fails, its studies get the prior row. `predict_dirs` is now
  `predict_raw` + `combine_raw` (same output as before).
- **Notebook** (`notebooks/infer.py`): `--gpus auto` (default) uses every visible GPU; `--workers` is split across
  them (3 → 2 per GPU on 4 vCPUs). `run_summary.json` gets `multi_gpu` (shard sizes, per-shard arm-load time, retries).
  One GPU / CPU = the old path.
- **Training** (`src/knee/train/multi_fold.py`): a fold queue. Each fold is a normal `train_sup` process pinned to
  one GPU with `CUDA_VISIBLE_DEVICES`; when a GPU frees up, the next fold starts. `--hours` budget: at the deadline
  every running fold gets a STOP file (saves `last.pt`), nothing new starts, and re-running the command resumes.
  `train_sup` gained `load_cfg` / `resolve_dirs` (split out of `main`, same behaviour).
- Not DDP, on purpose: we need 5 folds anyway, and independent folds give the same throughput without gradient sync,
  trainer changes, or a shared failure. Not DataParallel at inference: the forum reports host-RAM OOM on the hidden
  test, and it would only split the model work, not the preprocessing.
- Tests: `tests/test_multi_gpu.py` (5): two 'cpu' shards = single process for both mean and rank blends (random
  weights, 1e-6); dead shard → retry → fallback rows; balanced shards; the launcher runs folds 0 and 1 at the same
  time on different GPUs and fold 2 waits for a free one. Full suite: 145 passed, 2 skipped.

### Learning notes
1. **Why the blend must run after the shards are merged.** A rank blend turns each arm's scores into ranks across
   studies. Ranking within each half separately would give two half-sized rankings that don't compare with each
   other, and AUC reads exactly that cross-study order. Means are per-study and would be fine, but doing it once in
   the parent keeps both correct.
2. **Spawn vs fork.** A forked child inherits the parent's CUDA state, which CUDA doesn't support; spawn starts a
   fresh interpreter, so each child initializes its own GPU. That's also why children load the checkpoints
   themselves.
3. **Data parallelism vs task parallelism.** DDP splits one training run across GPUs and syncs gradients every step.
   With 5 folds to train, running two independent folds is "embarrassingly parallel": same total throughput, zero
   communication, and a crash only loses one fold.

## Addendum: quota billing (Dom asked, same day)
GPU quota is per account (30 h/week across all notebooks, resets Saturday 00:00 UTC) and is charged per session wall-clock, not per GPU: the P02 profile ran 411 s on a T4 ×2 session and `kaggle quota` showed 0.12 h used (checked 2026-09-30; one data point). If it bills per GPU it would have shown ~0.23 h. So the second T4 is free: two Track A folds at once ≈ 14 quota
hours instead of 28. Confirm on the first long two-fold session by reading `kaggle quota` before and after.
