    MONOCHROME1); robust (logs + returns None).
  - `geometry.py` (extended): **canonical frame**. `canonical_inplane_ops` finds the transpose/flips that put any
    acquisition (including transposed, flipped or ~15° oblique ones) into one fixed display per plane.

  - `normalize.py`: per-series 1–99 percentile window → uint8.

  - `dataset.py`: `CacheReader` (lazy memmaps, picklable for Windows spawn), `StudyWindowsDataset` (Track A),

  - `inspect_cache.py`: eyeball figures + DataLoader throughput bench.
- `tests/test_data.py`: 32 tests (all 8 transpose/flip layouts × 3 planes recovered exactly; laterality chain;
  fixed-mm scale; padding; slot choice; window helpers; end-to-end canonical order + mirroring on synthetic studies;
  **parity: cache bytes == direct `preprocess_study`**; both datasets + collate + pickling; a real-stub test behind

## Results (measured on the stub, Mac)
- Single process ≈ **4.2 ms/slice**, 0.3–1.4 s/study. 147 KB/slice at 384 px → full train ≈ **120 GB** (projection).
- Stub laterality: the tagged study is L (tag); the other two resolve R from geometry (|x| ≈ 85–99 mm, far outside
  any dead zone). IOP plane == CSV plane on all 13 readable series. 0 duplicate positions, 0 off-orientation slices.
- **Real-data check of the canonical frame** (`docs/figures/cache_check_mirrored_axial_stub.png`): the tagged left
  knee, after mirroring, shows the fibula on the image left at slice 0 (inferior), exactly like the native right
  knees; slices ascend tibia → femur/patella; anterior at the top.
- DataLoader on a warm cache: 150–225 studies/s (2 workers, 384 px). That's far above the GPU's rate, but cold-disk numbers need Windows.

Design choices to check:
- **Full canonical frame instead of the brief's "flip LR for cor/ax, reverse sag".** Same effect for normal acquisitions,
  but it also fixes series stored transposed or flipped (the public notebooks only handle laterality).
- **Unknown laterality → no mirror** (a wrong flip is worse than none). The 20 mm dead zone is a placeholder until
  S01 part 2's |x|-band table.
- **Pad, don't stretch**, when the FOV < 130 mm (the public caches skip the crop instead, which changes the mm scale).
- The percentile window is computed after the resize and excludes the padding.
- Slot ranks (fluid: PD > T2 > STIR > GRE; other: PD > T1 > T2) are guesses from knee protocols. Your MRI knowledge beats
  mine here.
- Everything is stored at 384 px, all slices of all series (Track B's bag and MAE want every series). Downsampling at
  load is cheap; re-caching is not.

Learning notes:
1. **Why a mm-based crop beats a pixel crop.** Scanners use different matrices (512–960 px) over different FOVs
   (150–320 mm), so "the central 384 pixels" covers 60–120 mm of anatomy depending on the scanner. Cropping 130 mm and
   resampling to 384 px makes every pixel 0.34 mm everywhere. A meniscus is then the same number of pixels (and the
   same number of ViT patches) in every study, so the model doesn't have to learn scale invariance from 4k studies.
2. **How IPP·normal gives physical order.** IOP's two vectors span the slice plane; their cross product is the normal.
   Each slice's IPP is a 3D point, and its dot product with the normal is "how far along the stack" that slice sits, in mm.
   Sorting by it gives true anatomical order. Filenames are random UIDs, and InstanceNumber ran backwards in 12/14 stub
   series. We also flip the normal's sign to a fixed patient direction, so slice 0 always means the same side of the knee.
3. **What a 2.5D window is.** Three neighbouring slices (≈3–4 mm apart) go into the 3 input channels. A 2D network then
   sees a little through-plane context (a meniscal tear that appears in consecutive slices, fluid tracking between slices)
   at 2D cost. Full 3D would triple the tokens per window, and the slices are 10× farther apart than the pixels anyway.
4. **Why the cache is a uint8 memmap.** 120 GB can't fit in 16 GB of RAM. A memory-mapped file lets the OS page in
   only the slices a batch touches, and each DataLoader worker maps the same file without copying it. uint8 is 4× smaller
   than float32 and loses nothing that matters: the percentile window already sets the contrast, and 256 grey levels
   exceed what the model resolves. Writing a study's series back to back makes one study one sequential read, which is
   what SSDs are fastest at.
