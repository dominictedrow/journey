# S01 part 1 — 2026-09-24 — Environment + data audit code (Mac)

"Phase 1" of the plan is S01, the first build session. The brief assumes the Windows box (GPU + the 570 GB SSD).
This part ran on the Mac, so it built and tested everything that doesn't need them and measured what the Kaggle CLI can
reach: the CSVs and the visible test stub. Part 2 is one script on the Windows box (`scripts/run_s01.ps1`).

## Done
- **Audit code** in `src/knee/audit/`:
  - `env_check.py`: hardware (physical vs logical cores, RAM, drives), GPU + driver, torch/CUDA, sm_120, bf16/fp16
    matmul, the SDPA backends, torch.compile, a 2-worker spawn DataLoader, decoders on 4 syntaxes, and the Kaggle CLI.
    Writes a generated block in `docs/env.md`.
  - `csv_audit.py`: counts, gold prevalence, plane/flag crosstabs, report lengths/languages/duplicate hashes.

  - `header_scan.py`: reads every header (no pixels) with a process pool in resumable shards. For each file it stores
    geometry, sequence and scanner fields, plus a truncation check (file shorter than header + expected pixel bytes).
    For the corpus it counts every tag with example values; UIDs and PatientID are redacted.
  - `series_summary.py`: per-series geometry and slice-order checks, contrast class, header fat-sat and laterality
    (tag + geometry). Per-study laterality consensus and the scanner-fingerprint site proxy.
  - `decode_bench.py`: re-encodes a real file into every syntax, checks each decoder plugin gives bit-exact output,
    then measures cold multi-process throughput on real files.
  - `write_reports.py`: renders `docs/data_audit*.md` and `docs/dicom_tags*.md` (aggregates only).

  - `geometry.py`: IPP·normal slice ordering, plane from IOP, in-plane axis letters, obliquity, image centre,
    laterality heuristic, spacing stats.
  - `series_meta.py`: contrast class (T1/PD/T2/STIR/GRE with a description fallback), fat-sat tokens, manufacturer
    normalization, scanner fingerprint.
- `tests/`: 15 pytest tests (geometry, sequence rules, report hashing, and an end-to-end scan of a synthetic series with a
  truncated file and a stray .txt). All pass on the Mac.
- `requirements.txt` pinned (torch 2.14.0+cu130 for Blackwell; resolves for Windows/py3.12). `pyproject.toml` (`pip install -e .`).
  `configs/paths.example.yaml`. `scripts/run_s01.ps1` runs the whole audit in order.
- Docs: `docs/data_audit.md` (§1–4 from the real CSVs), `docs/data_audit_test.md` + `docs/dicom_tags_test.md` (test stub),
  `docs/env.md` (skeleton + what the Mac verified). CLAUDE.md, HANDOFF, the master plan and the S01 brief are updated.

- **4,407 studies, 58 gold (4,349 unlabeled, 0 partial), 24,371 series**, 3–14 series/study (median 5). Matches the notebooks.
- Fluid_Sensitive == Fat_Suppression on **24,371 / 24,371** rows. Every study has all three planes.
- Gold prevalence: exactly as in `docs/kaggle` (MCL 9 positives, Lateral OA 11, Baker's 12 …). No all-negative gold study.
- Reports: 223 studies share a normalized text in 52 groups (largest 37). One gold study shares its text with another study.
  Rough languages: en 1,796, es 682, tr 488, hr/sr/bs 406, Greek 321, de 260, Cyrillic 220, nl 151, fr 79.
- Test stub (512/558 files; the Kaggle API returned HTTP 429 for the rest):
  - 100% Explicit VR LE; 0 header errors; 0 truncated files; 69 distinct elements; no overlays or private tags.
  - IOP-derived plane matches the CSV plane 14/14.
  - InstanceNumber runs *against* physical position in 12/14 series, and filename order is random (51%).
  - Geometry laterality matches the tag on the one tagged study (|centre x| is 80–93 mm, far from 0).
- Decoders: Implicit VR, JPEG Lossless SV1, JPEG 2000 and RLE re-encodings of a real slice all decode **bit-exact**.
  Warm decode on the Mac: ~0.5 ms/slice uncompressed vs ~12 ms (JPEG Lossless) and ~18 ms (JPEG 2000) for a 960×960
  slice. With pylibjpeg, JPEG 2000 took ~67 ms, so **prefer gdcm for JPEG 2000**.

## Surprises
1. **Toshiba files carry far fewer tags.** No TR/TE, ScanningSequence, MagneticFieldStrength, PatientSex or Laterality
   (on the test stub; [H17] saw the same 4.3% pattern in train). The contrast class now falls back to SeriesDescription
   ("SG PD FatSat", "CO T2W FS"). The site proxy for these studies is just "Toshiba|model|?T|?".
2. **The CSV's `Fluid_Sensitive` flag looks like "fat-suppressed", not "fluid-sensitive".** A T2 TSE sagittal *without*
   fat-sat is 0, and a 3D water-excitation GRE is 1. On the stub, header fat-sat matches the flag 14/14. If the full corpus
   agrees, non-FS T2/PD series are "other" in the slot layout, and the header contrast class is the only way to tell them
   apart. Worth a look from Dom (it affects the slot definitions in S02).
3. `SpacingBetweenSlices` was missing in 6 of 14 stub series (vs 5.7% in [H17]'s train sample). Always derive the spacing
   from IPP differences.
4. The Kaggle API rate-limits single-file downloads after ~500 in a few minutes (HTTP 429). Don't plan on pulling DICOMs
   file by file.

Design choices to check:
- The tag inventory covers **every file**, not the brief's ~500-file sample. It costs nothing extra because the header is
  read anyway, and it gives exact present-rates.
- The laterality rule is reported *by |centre x| band* so part 2 can pick a dead zone from data, not by guessing.
- The site proxy is manufacturer | model | field strength | software (no InstitutionName exists). [PROBE] also used the
  coil name and got 265 groups; we can add it if 5 folds come out unbalanced.

Learning notes:
1. **Transfer syntaxes.** A DICOM's pixel bytes can be stored raw (Explicit/Implicit VR Little Endian differ only in
   how the *header* is encoded) or compressed (JPEG Lossless, JPEG 2000). Raw decoding is a memory copy (~0.5 ms/slice);
   compressed needs a codec (gdcm/pylibjpeg) and costs 10–40× more CPU. For the efficiency prize, that's the difference
   between inference being disk-bound and CPU-bound.
2. **Why IPP·normal beats filename order.** IOP gives two in-plane direction vectors; their cross product is the direction
   the stack advances. Projecting each slice's IPP (its 3D corner position) onto that normal gives its true depth in mm.
   Filenames are random UIDs (51% pairwise agreement = coin flip), and InstanceNumber ran backwards in 12 of 14 stub
   series. Sorting by either would scramble or mirror the volume, which matters for a model that learns slice order.
3. **Pixel spacing and patch size.** Spacing here runs ~0.16–0.35 mm/pixel, so a 16-pixel patch covers 2.5–5.6 mm of
   anatomy depending on the scanner. A ViT patch should mean the same physical size everywhere, which is why S02 crops a
   fixed number of *millimetres* (e.g. 130–140 mm) and then resizes to a fixed pixel grid. The slices are ~10× farther
   apart (3–5 mm) than the pixels, so through-plane and in-plane resolution differ a lot. That's why we tokenize per slice
   and sample slices instead of cutting cubic 3D patches.
