# Questioning: Phase 2 · Collectors (point-in-time)

> Ask Dom **one question at a time**. Record each answer under the question as `**A:**`. When every question is answered, write `docs/components/02_collectors.md`, covering interfaces, config keys, tests and acceptance criteria.
> Spec reference: Data collection, Point-in-time rules

1. **Universe:** what does the weekly screen start from? Options: the S&P 500, the S&P 500 plus the Nasdaq-100, or the Russell 1000. How big should the tradable universe be (the spec implies about 60 stock candidates)?
   **A:** **S&P 500** only (point-in-time membership via fja05680, so backtests avoid survivorship bias). Weekly screen outputs **~80 candidates** (not the spec's ~60); the count is a config key, not hard-coded. (Dom, S02)
2. **Crypto universe:** BTC, ETH and SOL plus which altcoins? Should it be every Alpaca-tradable coin that passes the $50M ADV filter?
   **A:** Option 2 (D-021). **Pool** = every USD-quoted coin Alpaca can trade (Assets API, checked each run), minus stablecoins; no hand-picked list. **Liquidity** = CoinGecko global 30-day ADV ≥ $50M, not Alpaca venue volume (probe 2026-11-25: Alpaca 30-day ADV was BTC ~$203k, ETH ~$57k, SOL ~$35k, so a $50M filter on it excludes everything). Collect daily bars for the whole pool, including coins that fail the filter today. (Dom, S02)
3. **Backfill depth:** 10 years (2016 onward, the limit of Alpaca's free history), or go further back with yfinance?
   **A:** **Prices:** Alpaca 2016+ is the primary record for every stock, ETF and crypto (confirm Alpaca crypto start date in build). **yfinance pre-2016:** only index-level series (SPY, QQQ, sector ETFs) back to ~2000, for the HMM regime model; stored as separate `source='yfinance'` rows, never mixed into the Alpaca record, never used for per-stock features. **Macro:** full FRED/ALFRED history. (Dom, S02)
4. **ALFRED:** should training use first-release vintages for every macro series, or only for the revised ones (CPI, PCE, GDP, UNRATE)?
   **A:** **As-of vintages, every series** (not first-release only). Store every ALFRED vintage as append-only rows (obs date, value, vintage `released_at`); features use the latest vintage with `released_at <= T`. One code path for all series; rarely-revised market series get `released_at` = obs date + publication lag (e.g. VIXCLS next morning). Exception (D-001): `BAMLH0A0HYM2` is truncated on ALFRED, so we archive our own daily snapshots with `released_at` = fetch time. (Dom, S02)
5. **Historical S&P membership (fja05680):** before our first stored screen, OK to accept and document its known gaps in the early years?
   **A:** Accept and document. Its gaps are mostly pre-2005, outside our 2016+ per-stock window. Use fja05680 (own rows, `source='fja05680'`) from 2016 up to our first stored screen; from then on our own weekly membership snapshots (`released_at` = snapshot time) are authoritative. One-time cross-check at load against a current constituents list, with differences logged and documented, not hand-patched. Ticker changes (e.g. FB → META) map through the aliases table (Q7). (Dom, S02)
6. **News:** collect every article from the 5 feeds now, before the quota and SVM exist? (Recommended: yes. Store everything; filtering happens downstream.) How often should we fetch: hourly or every run?
   **A:** Yes, collect every article from all 5 feeds now; filtering happens downstream. Fetch every **15 minutes** (RSS windows are short, so hourly risks losing items). Dedupe on URL/GUID. Store `published_at` (feed) and `released_at` (first seen by us); point-in-time features use `released_at`. (Dom, S02)
7. **Aliases table:** how should the ticker → company names and short-names list be built (EDGAR company names plus manual additions)?
   **A:** Base = EDGAR `company_tickers.json` (ticker, CIK, registered name). Auto short names by stripping legal suffixes (Inc., Corp., Holdings, plc, Class A). Manual additions in reviewed `configs/aliases.yaml` (e.g. Google → GOOGL/GOOG, Facebook → META), including crypto aliases (Bitcoin/BTC, Ethereum/Ether/ETH, Solana/SOL, one per pool coin). Ambiguous common-word names (Target, Visa, Gap, Ball, Ford, Apple) are flagged: case-sensitive match only, plus a finance cue (shares/stock/ticker) in the article. Every alias row has `valid_from`/`valid_to` for point-in-time mapping. (Dom, S02)
8. **Congress.gov:** which committees and bill statuses count as "finance, tax and appropriations"? Should Fed speeches be included?
   **A:** Committees (8): House Ways and Means, Financial Services, Appropriations, Budget; Senate Finance, Banking, Appropriations, Budget. Event statuses: reported by committee, passed a chamber, conference/resolving differences, sent to President, became law, vetoed. Introductions stored but not counted as events. Debt-ceiling and CR/shutdown bills tagged explicitly. Fed speeches: **yes, in the Fed collector** (federalreserve.gov speeches RSS, tagged by speaker so Chair/Governors are distinguishable from regional presidents), not in the Congress collector. Needs a free api.data.gov key (Dom to sign up; add to `.env.example`). (Dom, S02)
9. **Crypto derivatives (D-006):** which symbols' funding and open interest (BTC and ETH perps only)? How should venues be combined (OI-weighted average)?
   **A:** Coins: **BTC, ETH, SOL** perps (match crypto core). Funding: normalize each venue to annualized (OKX 8h, Hyperliquid 1h), combine as OI-weighted average using each venue's own OI. OI: USD sum across all 4 venues (contracts → USD at venue mark price). Raw per-venue rows (venue, symbol, rate, OI, `released_at`) in raw tables; aggregates computed downstream as features. A missing venue → aggregate from the rest + warning; all funding venues missing → NaN → NO TRADE for crypto risk. Backfill whatever each venue's public API exposes (OKX ~3 months funding), then daily snapshots. (Dom, S02)
10. **SoSoValue (D-007):** if its key turns out to be free, use it. If not, drop ETF flows. Any objection?
   **A:** No objection. Verify in the build session (sign up, confirm the free tier covers daily US spot BTC ETF net flows, record in API_REGISTRY). Free → collect daily net flows + available history, `released_at` = fetch time. Not free → drop from v1 with a DECISIONS entry; the 5-day ETF-flow feature is left out, not proxied. ETF flows are **non-critical**: missing values never trigger NO TRADE. (Dom, S02)
11. **Daily job timing:** confirm the 16:30 ET collect. Crypto trades 24/7, so which cutoff defines the crypto "daily close" (00:00 UTC, or 16:00 ET)?
   **A:** (a) Stock collect = **XNYS market close + 30 min** (16:30 ET normally, 13:30 on early closes); the offset is a config key. (b) Crypto daily close = **00:00 UTC**, Alpaca's native 1Day bar boundary (verified 2026-11-25: bar `t` = `YYYY-MM-DDT00:00:00Z`), also the CoinGecko/funding standard, and DST-free. Crypto collect runs at **00:15 UTC** (buffer for late bars). Point-in-time: crypto features at T use only bars closed (00:00 UTC) ≤ T; the 16:30 ET decision sees a ~16 h old crypto bar, acceptable on a 7-day horizon. (Dom, S02)
12. **EDGAR User-Agent:** what app name and contact string should we send (kept in `.env`)?
   **A:** `SEC_EDGAR_USER_AGENT="quant_trader <email>"` in `.env` only (Dom chose the contact email; set 2026-11-25, never committed). Collector refuses to start if it's missing or has no `@`. Throttle ≤ 10 req/s (SEC fair-access limit), config key. (Dom, S02)
